# music app 投屏调试记录

2026-11-21。从「只能放本地 48 kHz WAV」到「QQ 音乐 SQ 投屏零卡顿」的完整过程。
每个坑都附了当时的实测数字，方便以后遇到同样症状时对照。

**起点**：`pos` 增速 0.43x，`peak` 恒 32767（满幅噪声），每 5 秒断续十几次。
**终点**：`pos` 增速 1.000x，`underrun` 全程 0，两个 ring 灌满，无卡顿无破音。

---

## 一、核心逻辑的三次演进

### 1. 最初：单线程同步

```
播放任务：http read 8 KB ─► decode ─► esp_codec_dev_write（阻塞到 DMA 排空）
```

I2S DMA 队列只有 `6 × 240 帧` ≈ **33 ms**。任何一次 read 超过 33 ms，喇叭就没数据了。
网络抖动、解码耗时、codec 重配全部串在一起，一有波动就断音。

### 2. 第二次：PCM 抖动缓冲 + 独立写任务

```
播放任务：read ─► decode ─► PCM ring 512 KB
写任务　：PCM ring ─► esp_codec_dev_write
```

把「I2S 写入阻塞」从播放线程里摘出去，网络/解码波动只消耗缓冲余量。
这一版解决了持续性卡顿，但 `read + decode` 串行只剩 14% 余量，扛不住 70 ms 尖峰。

### 3. 最终：三段流水

```
music.net  (prio 6):  http read 8 KB  ──►  压缩流 ring 128 KB
music.play (prio 5):  ring ──► decode 12 ms ──► PCM ring 512 KB
music.i2s  (prio 7):  PCM ring ──► esp_codec_dev_write
```

- `music.net` 是**唯一**的 http 读方，独占 `esp_http_client_handle_t`
- 播放任务通过命令队列（`s_net_req_q`）发 OPEN/CLOSE，不再直接碰 http
- reader 回报状态：`IDLE / OPENING / OPEN / FAILED / EOF / LOST`
- 断线时先播完 ring 里的余量，再按当前进度 Range 重开
- reader 用专用 `s_net_in_buf`，避免和本地播放的 `fread(s_in_buf)` 抢同一个缓冲

最终生产速率：read 3 ms/8 KB（约 2.6 MB/s 能力）vs 消费 212 KB/s，余量十几倍。

## 二、踩坑清单（按发现顺序）

### 坑 1 · 24 bit PCM 被当 16 bit 播放

**证据**

```
W music.player: decoded 24-bit PCM, expect 16-bit for best result   ← 每帧刷屏
dlna pos 7594/279000 ms, peak 32767          ← 恒满幅
per-chunk 间隔 170 ms，而一帧 FLAC 只有 93 ms 音频
pos 增速 0.43x
```

**根因**：`esp_audio_simple_dec` 对 24 bit FLAC 输出 3 字节打包的 PCM，直接喂给按 16 bit
打开的 I2S，等于把数据错位解释 —— 满幅噪声 + 时长错乱。

**修复**

- `apply_dec_format()` 把喇叭统一按 `min(dec.bits, 16)` 打开
- `pcm24_to_s16()` 原地收窄（3 字节小端 → 取中间字节和高字节，输出比输入短，原地安全）
- `s_pcm_bits` 记录解码器**真实**输出位深，写之前查它
- `s_net.byte_rate` 按**实际写入**的位深算，进度才不跑偏

**效果**：`peak` 回到 16000~29000（正常音乐范围），0.43x → 0.53x。

### 坑 2 · 打不开的格式每帧 close/open

**证据**：速度掉到约 0.5x，连续卡顿；日志里格式警告每帧一条。

**根因**：`audio_apply_format()` 失败后没有记忆，下一帧又 `esp_codec_dev_close` +
`audio_open_format` 一次。ES8311 每次要重写几十个 I2C 寄存器并停/启 BCLK/MCLK，
单次毫秒级，每秒几十次就把播放任务吃光。

**修复**：`s_bad_rate/s_bad_ch/s_bad_bits` 记住打不开的格式，命中直接返回 `ESP_FAIL`；
某次成功打开则清空。新格式失败时回退旧格式，别把本地播放也弄哑。

### 坑 3 · 结构性问题：I2S DMA 只有 33 ms，而 read 要 60 ms

**证据**

```
per-chunk read 71/61/38/83 ms   dec 3 ms   write 19 ms
pos 增速 0.835x
```

**根因**：单线程 `read → decode → write` 串行。每 5 秒有 20 次 read，累计 1.2 秒完全
不往 I2S 写字节，而 DMA 队列只有 33 ms。

**修复**：PCM `StreamBuffer` 512 KB（PSRAM）+ 独立写任务 `music.i2s`（prio 7）。
暂停/停止/拖动/切格式都会 `pcm_fifo_flush()`，不会把旧数据按新位置播出去。

### 坑 4 · TCP 接收窗口只有 5760 B

**证据**：`CONFIG_LWIP_TCP_WND_DEFAULT=5760`（4 × MSS）；一次 8 KB read 约 60 ms，
吞吐 ≈ 130 KB/s，而 SQ 需要 212 KB/s。

**根因**：窗口装不下一次 read，要等好几个 RTT。

**修复**：调到 `24576`。副作用是吃内部 RAM，见坑 5。

### 坑 5 · 内部 RAM 被挤到只剩 20 KB（比卡顿更严重）

**证据**

```
E spi_common: spicommon_dma_setup_priv_buffer(460): Failed to allocate priv TX buffer
E co5300_spi: send color data failed
E esp_lvgl:bridge_v9: Draw bitmap failed: ESP_ERR_NO_MEM
int=20071 dma=7007 dma_max=31744     ← DMA 只剩 7 KB
```

**根因**：`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384` 让 ≤16 KB 的分配强制留在内部 RAM，
FLAC 解码器的中等块全挤在这里；再叠上 TCP 窗口和 http 缓冲，屏幕 SPI 连 DMA 缓冲都分不到。

**修复**：`ALWAYSINTERNAL` 降到 `8192`。

**效果**：`int` 20 KB → 98~102 KB，`dma` 7 KB → 91~94 KB，SPI 报错全部消失。

### 坑 6 · Wi-Fi modem sleep 造成 50~150 ms 收包尖峰

**证据**

```
I wifi:pm start, type: 1        ← WIFI_PS_MIN_MODEM，等 DTIM 才收包
per-chunk read 15~27 ms，但偶发 57 / 70 / 145 ms
underrun 12 / 17 / 12 / 7 ...
```

**修复**：连上 Wi-Fi 后 `esp_wifi_set_ps(WIFI_PS_NONE)`（改在 `music_dlna.c`，只影响本 app）。

**效果**：read 尖峰消失，`pos` 从 0.82x 涨到 0.998x。

### 坑 7 · 为省内存把 TCP 窗口压到 8192（过度优化的反噬）

**证据**：`read` 36 ms，生产 0.77x，`pos` 0.916x，`underrun` 12~17/5s。

**教训**：8 KB 窗口"看着刚好装下一次 8 KB 读"，实际还要额外等 RTT 才能填满。
最终定在 `24576`，并把这条写进 `sdkconfig.defaults` 的注释里，防止以后又为了省内存改小。

### 坑 8 · read 与 decode 串行，只剩 14% 余量

**证据**：`read 20 + dec 13 = 33 ms`，而 8 KB 压缩数据对应 37.7 ms 音频。

**修复**：拆成 `music.net` 任务 + 128 KB 压缩流 ring（见第一节）。

### 坑 9 · 异步化引入的 CLOSE / OPEN 竞争（投屏直接失败）

**现象**：投屏后 UI 显示"播放失败"。

**根因**：重构后 `net_close_http()` 变成"发 CLOSE 命令"，而 `net_open()` 开头仍调用它：

```
播放任务:  发 CLOSE ──┐
播放任务:  state = OPENING，发 OPEN
reader:    处理 CLOSE → state = IDLE        ← 覆盖了 OPENING
播放任务:  等不到 OPEN，判"拉流失败"
```

**修复**：`net_open()` 只发 OPEN，reader 收到 OPEN 时自己先关旧连接；
reader 的 CLOSE 分支加保护，`OPENING` 期间不改状态。

### 坑 10 · 拉流循环里的 50 ms 队列等待 = 吞吐上限（最隐蔽的一个）

**证据**

```
read 3 ms × 95 次/5s           ← 每次读很快，但 5 秒只读了 95 次
pcm 0~16 / 512 KB   raw 0 / 128 KB   ← 两个 ring 都空
feed 700~776 KB/5s = 140 KB/s  ← 需求 192 KB/s
pos 增速 0.77x，underrun 5~12/5s
```

**根因**

```c
/* 每轮循环开头，用 50 ms 超时等命令 */
if (xQueueReceive(s_net_req_q, &req, pdMS_TO_TICKS(50)) == pdTRUE) { ... }
```

等于每读 8 KB 就白等 50 ms：`1000/50 × 8 KB = 160 KB/s`，恰好是 SQ 需求的 3/4。
日志里 `read` 只有 3 ms，极具欺骗性 —— 看起来网络很快，实际是被自己节流了。

**修复**：命令队列改 `timeout = 0` 非阻塞轮询，只有空闲（无连接）时才阻塞等命令。

**效果**

| | 修复前 | 修复后 |
|---|---|---|
| read 次数 | 95/5s | 110~151/5s |
| feed | 140 KB/s | 189 KB/s |
| pcm / raw 水位 | 0~16 / 0 KB | 508/512 / 127/128 KB |
| underrun | 5~12 | **0** |
| pos | 0.77x | **1.000x** |

### 坑 11 · 切歌后 CDN 预热期吞吐只有 180 KB/s

**证据**：切歌后 `read` 40~54 ms，`underrun` 25~32 持续约 20 秒，之后自己恢复。

**修复**：`MUSIC_PREFILL_BYTES=320 KB` / `MUSIC_PREFILL_MS=2500` —— 新流先静音攒够
1.7 秒（实测这首 `prefill 327680 B in 1576 ms`）再出声。用"晚 1~2 秒开始"换掉前 20 秒断续。

### 坑 12 · 烧录链路的三个陷阱

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| `idf.py flash` | 写 `0x20000` 覆盖 selector，长按 BOOT 回不去 | 用镜像库发布 + selector 启动 |
| `flash_dev.ps1` 写 `ota_0` | 下次从 selector 启动时被 `storage` 里的旧 bin 覆盖 | 只用于临时验证，不能作为发布通路 |
| `pack_storage.ps1 -Flash` 中途断电/重启 | storage 分区半写，镜像损坏 | 重跑一次，确认 `Hash of data verified` |

**排查技巧**：`esptool verify-flash 0x220000 build/music.bin` 能直接判断
`ota_0` 里跑的是不是刚编译的那版，比看日志猜快得多。

## 三、关键参数与为什么

| 参数 | 值 | 为什么 |
|---|---|---|
| `CONFIG_LWIP_TCP_WND_DEFAULT` | **24576** | 5760 → read 60 ms；8192 → 36 ms（会断续）；24576 → 15~30 ms |
| `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` | **8192** | 16384 时 FLAC 曲目内部 RAM 只剩 20 KB，屏幕 SPI 分配失败 |
| `MUSIC_PCM_FIFO_BYTES` | 512 KB | 48 kHz 立体声约 2.7 s 余量，PSRAM |
| `MUSIC_RAW_FIFO_BYTES` | 128 KB | 压缩流，SQ 下约 0.6 s，PSRAM |
| `MUSIC_PREFILL_BYTES` / `_MS` | 320 KB / 2500 | 避开 CDN 切歌预热期 |
| `esp_http_client` `buffer_size` | 2048 | 内部 RAM 要和 FLAC 解码器、屏幕 DMA 共用 |
| reader 任务栈 | 8192 | `esp_http_client_open()` + header 解析吃栈，4 KB 偏紧 |
| `MUSIC_NET_OPEN_TIMEOUT_MS` | 10000 | 等 reader 建连的上限，超时直接报错别干等 |

任务优先级：`music.i2s` 7 > `music.net` 6 > `music.play` 5 > DLNA 4。
喂喇叭必须最高，否则 DMA 会被别的任务拖空。

## 四、诊断日志判读

每 5 秒一条：

```
dlna pos 22357/279000 ms, peak 22682, int=71655 dma=63867, fmt 48000/2/16 pcm24,
read 3 dec 13 write 84 ms (125 rd/59 wr), underrun 0,
pcm 508/512 KB raw 127/128 KB feed 944 KB/236
```

| 现象 | 结论 | 看哪里 |
|---|---|---|
| `pcm` 接近 0 + `underrun` > 0 | 生产端供不上 | 看 `raw` 水位 |
| `raw` 也接近 0 | 网络侧供不上 | 看 `read` 次数（< 60/5s 说明被节流） |
| `raw` 满、`pcm` 空 | 解码慢或播放任务被阻塞 | 看 `dec` |
| `feed` 远低于 192 KB/s | 解码输出不足（格式判断错/丢帧） | 看 `fmt`、`pcm24` |
| `peak` 恒 32767 | 位深/打包不匹配 | 看 `fmt` 与 `pcm` 位深 |
| `pos` 增长但 `underrun` > 0 | 缓冲在"刚够"边缘 | 加大 ring 或提升生产 |

**判读顺序**：`underrun` → `pcm` 水位 → `raw` 水位 → `read` 次数。
前三步就能把问题定位到网络 / 解码 / 播放三段中的一段。

## 五、经验教训

1. **先量化再改**：所有修复都基于 `pos` 增速、`per-chunk` 耗时、ring 水位这些数字，
   没有一次是靠"感觉像解码慢"去改的。剖析日志（read/dec/write + 两个水位）是这轮
   最有价值的投入。
2. **ring 水位比平均耗时更能说明问题**：平均值好看不代表不卡，水位是否见底才决定听感。
3. **循环里的阻塞等待会变成吞吐上限**：坑 10 的 50 ms 队列等待就是典型 ——
   任何"每轮 sleep/等一会儿"都要算一下它隐含的速率上限。
4. **异步化要重新检查隐含依赖**：`net_close_http()` 从同步变异步后，它在 `net_open()`
   里的调用顺序就变成了 bug。
5. **省内存的参数要成对看**：TCP 窗口省 8 KB 内部 RAM，代价是 read 从 20 ms 涨到 36 ms，
   直接把播放速度从 1.0x 打到 0.77x。省内存前先确认不会踩到实时性红线。
6. **不同曲目/不同 CDN 节点表现不同**：同一首 FLAC 有时 read 20 ms、有时 40~54 ms，
   所以缓冲余量要按"最差情况"设计，不能按平均值。
